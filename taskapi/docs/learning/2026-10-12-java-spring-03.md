# 2026-10-12 Java·Spring 학습 일지

- 프로젝트: 팀 업무 관리 API (`taskapi`)
- 목표: 이전에 작성한 Task 엔티티·JPA 저장소를 포함해 전체 테스트를 검증하고 다음 학습으로 연결한다.

## 오늘 이어간 흐름

10월 10일에는 PostgreSQL 연결 이후 Task 엔티티 매핑과 JpaTaskRepository를 작성했다. Task의 테이블 이름은 tasks이며, ID는 DB가 자동 생성하고 상태는 문자열로 저장한다. JPA용 protected 기본 생성자를 추가하고 로컬의 ddl-auto 설정을 update로 바꿔 테이블 구조를 확인했다. psql의 -d에는 테이블 tasks가 아니라 DB taskAPI를 지정해야 한다는 차이도 다뤘다.

조력자가 JPA 테스트 틀을 준비하고 학습자가 핵심 호출·검증을 작성했다. 리뷰에서 boolean끼리 비교하던 ID 검증과 빈 Optional을 null로 비교하던 검증을 설명했다. 학습자 요청으로 조력자가 전체 테스트 파일을 수정했고, 저장 후 flush·clear로 영속성 컨텍스트를 비운 뒤 재조회하도록 했다. 새 테스트 3개는 10월 10일 통과했지만 전체 실행은 남아 있었다.

오늘 학습을 재개하며 기존 31개와 신규 3개를 합친 전체 테스트 실행부터 안내했다. 공유 로그에서는 localhost:5432 연결 거부가 발생했고 DB가 필요한 컨텍스트 1개와 JPA 테스트 3개가 실패했다. 일반 단위 테스트 30개는 통과했다.

조력자가 컨테이너 상태를 조회했을 때 PostgreSQL 컨테이너는 실행 중이었지만 PORTS에는 5432/tcp만 표시되고 호스트 주소 연결이 없었다. compose.yaml에는 127.0.0.1:5432:5432가 선언돼 있었으나 실제 컨테이너의 포트 연결과 달랐다. 설정 파일과 실제 실행 환경을 각각 확인해야 한다는 점을 다뤘다.

docker compose up -d --force-recreate postgres로 컨테이너를 재생성하고 docker compose ps에서 호스트 포트 연결을 확인하도록 안내했다. 이름 있는 볼륨은 유지하며 데이터 삭제를 동반하는 down -v는 사용하지 않도록 설명했다. 연결 실패 뒤 나온 Dialect 결정 오류는 DB 메타데이터를 읽지 못한 후속 오류라서 Dialect 설정부터 바꾸지 않았다. 학습자가 실제 수행한 복구 명령은 별도 출력으로 확인하지 않았다.

이후 학습자가 모두 통과했다고 보고했다. 조력자는 로컬 XML 결과에서 같은 실행 시각의 전체 34개 테스트가 통과했음을 확인했다. 오류가 해결된 최종 결과를 확인했으며, 테스트를 직접 재실행하지는 않았다.

## 검증 결과와 현재 범위

2026-10-12 18:02경(KST)의 XML 결과는 **34개 통과, 실패·오류·생략 0개**다. 구성은 컨텍스트 1, Task 4, 메모리 Repository 6, Service 20, JPA Repository 3이다. 오늘 처음 공유한 실패 실행과 이후 통과 결과를 구분해 기록한다.

이번에 확인한 JPA 기능은 실제 PostgreSQL 저장·재조회, 서로 다른 양의 ID 발급, 없는 ID의 빈 Optional 반환이다. 테스트의 Transactional은 데이터 변경을 종료 시 롤백하지만 ID 발급 번호까지 되돌리는 것은 아니므로 고정 ID를 기대하지 않는다.

Controller와 Service는 아직 메모리 TaskRepository를 사용한다. JPA 테스트 통과는 API 요청으로 생성한 업무가 DB에 저장된다는 뜻이 아니다. SQL 수정·삭제 연습은 이전 요청으로 생략했고 컨테이너 재생성 후 기존 데이터 유지도 별도 조회 결과로 확인하지 않았다.

## 다음 학습과 기록

다음은 업무 API의 저장소를 JPA로 전환하는 단계다. 수정·상태 변경의 트랜잭션, 없는 업무 처리, 목록 순서를 함께 다뤄 기존 API 계약을 유지해야 한다. 요구사항·완료 기준·작업 파일부터 안내하고 학습자가 구현한다. 테스트는 조력자가 틀을 준비하며 유사 테스트나 전체 보완은 요청 시 작성한다.

완료한 엔티티·저장소 단계의 커밋 메시지 후보는 `feat: Task 엔티티 매핑과 JPA 저장소 추가`다. 명세서를 갱신했으며 실제 커밋·푸시는 실행하지 않았다. 학습자의 이해나 감정은 대신 작성하지 않는다.

## 이어서 업무 API를 DB에 연결한 흐름

엔티티와 저장소만 JPA로 작성한 것과 실제 API가 그 저장소를 사용하는 것은 다른 단계임을 구분했다. TaskService는 아직 메모리 TaskRepository를 사용하고 있었으므로 JpaTaskRepository로 연결을 바꿨다. 학습자가 Optional 처리 방법을 질문해 반환 타입을 전부 바꾸지 않고 orElse(null)로 Task 또는 null을 반환하는 기존 Service 계약을 유지하도록 안내했다.

목록 정렬을 위해 작성한 findByTaskOrderByIdAsc는 존재하지 않는 task 필드를 조건으로 해석할 수 있어 findAllByOrderByIdAsc로 수정했다. 메서드 이름에서 검색 조건과 정렬 표현을 구분했다.

Service가 객체 대신 ID를 받아 조회부터 시작·완료·수정·삭제까지 처리하도록 학습자가 작성했다. Controller의 선행 조회를 없애고 Service의 결과를 HTTP 응답으로 변환하도록 맞췄다. 없는 업무는 상태 변경·수정에서 null, 삭제에서 false로 표현한다.

첫 리뷰에서는 Transactional이 빠져 있어 변경 응답만 확인해서는 DB 반영을 보장할 수 없음을 설명했다. 이후 생성·시작·완료·수정·삭제에 Spring Transactional이 적용된 것을 소스로 확인했다. 같은 트랜잭션에서 읽은 엔티티의 변경은 변경 감지로 반영하며 기존 Task의 업무 규칙은 유지했다.

조력자는 기존 Service 테스트의 준비 코드를 Spring 주입과 테스트별 롤백 방식으로 바꿨다. 학습자가 인수의 일괄 변경을 요청해 남아 있던 22개 호출을 객체에서 getId()로 수정했다. 컴파일 성공 후 학습자가 20개 통과를 보고했고 로컬 XML에서도 확인했다.

처음 통과 결과에는 영속성 컨텍스트를 비우는 코드가 없어 DB 대신 관리 중인 객체를 재확인할 수 있었다. 이를 설명하고 학습자 요청으로 정상 시작·완료·수정 테스트 6개에 flush·clear를 추가했다. 컴파일 성공과 이후 20개 재통과를 확인했다. 최신 XML은 18:43경(KST), 실패·오류·생략 0개이며 조력자가 테스트 자체를 재실행하지는 않았다. 테스트의 트랜잭션이 Service 호출을 감싸므로 실제 요청의 독립적인 커밋은 HTTP 검증과 구분했다.

실제 API 검증에서는 업무 생성 요청과 SQL 조회를 안내했다. 학습자가 공유한 tasks 조회 결과에서 ID 45, JPA API 검증, DB 저장 확인, TODO가 일치했다. psql 재접속 명령은 docker compose exec postgres psql -U admin -d taskAPI로 다시 안내했다. 시작 API 호출 후 DB IN_PROGRESS 확인은 학습자 통과 보고로 남긴다.

이후 제목·설명 수정, 완료, Spring 서버 재시작 후 조회, 중복 완료의 409, 삭제의 204, 삭제 후 조회·재삭제의 404와 DB에서 0행인지를 확인하도록 안내했다. 학습자는 긍정 응답을 했으나 개별 응답·SQL 결과를 공유하지 않았으므로 세부 결과를 직접 검증 완료로 단정하지 않는다.

마지막 '굿 테스트는 패스'는 전체 테스트 재실행을 생략하자는 요청으로 해석했다. 전체 34개 통과 기록은 API 전환 전이며 현재 전환 후 결과는 Service 20개 통과다. HTTP 오류 후 데이터 유지와 개별 재시작·삭제 결과의 명시적 증거도 남은 범위로 기록한다.

현재 구현은 API가 JPA 저장소를 사용하도록 전환된 상태다. 이번 변경의 커밋 메시지 후보는 `feat: 업무 API 저장소를 PostgreSQL JPA로 전환`이다. 실제 커밋·푸시는 실행하지 않았다. 전환 후 전체 회귀 테스트는 이후 필요한 시점에 수행할 수 있다.
