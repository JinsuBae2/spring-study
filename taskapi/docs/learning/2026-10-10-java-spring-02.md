## 오늘 이어간 흐름

DB·JPA 학습을 재개했다. 처음 제안한 H2 대신, 학습자가 사용해보지 않은 현업 기술을 경험하고 싶다는 방향에 따라 PostgreSQL을 선택했다. MongoDB도 비교했으며 PostgreSQL과 JPA를 먼저 학습하고, 문서형 저장 방식은 이후 비교 대상으로 남겼다.

첫 단계는 Docker Compose로 PostgreSQL을 실행하고 기본 SQL을 연습하는 것으로 정했다. Spring 연결과 Task 엔티티 매핑까지 한 번에 진행하지 않고, DB 실행·접속부터 확인한다. 일반 구현은 학습자가 직접 작성하며 요청할 때 힌트를 제공하는 방식을 유지한다.

Docker 설정을 직접 작성하는 것은 처음이라고 하여 compose.yaml의 틀과 .env 작성 방법을 안내했다. 학습자는 이 과정과 YAML 문법을 필수 학습 내용으로 기록해달라고 요청했다. 아래 내용은 안내한 개념이며 학습자의 이해 완료를 대신 판단한 기록은 아니다.

## Docker 설정과 YAML에서 다룬 내용

Dockerfile은 이미지를 만드는 방법을 정의하고, compose.yaml은 사용할 이미지와 서비스 실행 설정을 정의한다. 이번에는 공식 postgres:18 이미지를 사용하므로 별도 Dockerfile 없이 Compose 설정으로 시작한다.

YAML은 들여쓰기로 포함 관계를 표현한다. 탭 대신 공백을 사용하고 같은 단계의 항목은 들여쓰기를 맞춘다. 이번 예시는 단계마다 공백 두 칸을 사용한다.

```yaml
services:
  postgres:
    image: postgres:18
    ports:
      - "127.0.0.1:5432:5432"
```

- `키: 값`은 매핑이다. `image`의 값은 문자열 `postgres:18`이다.
- 값 없이 `services:`처럼 작성한 뒤 들여쓴 항목은 해당 키 아래의 구조를 이룬다. 여기서는 postgres 서비스가 services 아래에 속한다.
- `-`는 목록 항목을 표시한다. ports는 문자열 항목을 가진 목록이다.
- 문자열은 따옴표로 감쌀 수 있다. 포트 연결 값은 예시처럼 따옴표로 감싼다.
- `#`는 따옴표 밖에서 주석을 시작한다.
- `${POSTGRES_PASSWORD}`는 YAML 자체의 변수 문법이 아니라 Docker Compose가 처리하는 변수 치환 문법이다.

Compose 설정의 각 항목도 구분했다.

| 항목 | 역할 |
|---|---|
| services | 실행할 서비스 정의 |
| postgres | 직접 정한 서비스 이름 |
| image | 사용할 이미지와 태그 |
| environment | 컨테이너에 전달할 환경 변수 |
| ports | 컴퓨터와 컨테이너의 포트 연결 |
| 서비스 안의 volumes | 볼륨과 컨테이너 경로의 연결 |
| 최상위 volumes | 사용할 이름 있는 볼륨 선언 |

`127.0.0.1:5432:5432`는 컴퓨터의 루프백 주소에서 5432 포트를 컨테이너의 5432 포트로 연결하는 설정이다. PostgreSQL 18 공식 이미지의 볼륨 연결 경로는 `/var/lib/postgresql`로 안내했다. 이미지 버전이 다른 예제를 그대로 섞지 않도록 구분한다.

서비스 안의 `postgres_data:/var/lib/postgresql`에서 왼쪽은 볼륨 이름, 오른쪽은 컨테이너 경로다. 최상위 volumes에도 동일한 postgres_data 이름을 선언해야 한다. 컨테이너와 볼륨은 수명이 다르며, 볼륨을 보존하면 컨테이너를 재생성해도 DB 파일을 유지할 수 있다. 실제 유지 여부는 앞으로 검증한다.

.env는 YAML이 아닌 `이름=값` 형식이다. Compose가 .env에서 읽은 값을 `${POSTGRES_PASSWORD}`에 넣고, environment 설정을 통해 컨테이너로 전달한다. .env의 실제 비밀번호는 Git이나 일지에 남기지 않는다.

## 실행 중 만난 오류와 안내

처음 `docker compose config --quiet`를 실행하자 서비스가 미정의 볼륨 postgres_date를 참조한다는 오류가 발생했다. 서비스에서 참조하는 이름과 최상위 volumes에 선언한 이름을 postgres_data로 일치시키도록 안내했다. 두 곳의 이름은 임의로 정할 수 있지만 정확히 같아야 한다.

다음 실행에서는 postgres:18 이미지를 가져오기 전에 Docker API 소켓에 연결하지 못했다. 출력에는 `/Users/baejinsu/.docker/run/docker.sock` 경로가 없다는 내용이 있었다. 이 실행에서는 이전 볼륨 오류가 다시 표시되지 않았으나 설정 검증 성공 결과를 별도로 확인한 것은 아니다.

터미널의 docker 명령과 실제 컨테이너를 실행하는 Docker 엔진은 구분해야 한다. Docker Desktop이 실행되지 않았을 가능성을 설명하고, 앱 실행과 엔진 시작 대기 후 docker info로 연결 상태를 확인하도록 안내했다. 실제 원인 확정이나 해결 성공 보고는 아직 없다.

## DB 실행 확인 전의 확인 상태와 안내

- 학습자 공유 결과: Compose 볼륨 참조 오류, 이후 Docker 엔진 소켓 연결 오류.
- 조력자 직접 실행: 프로젝트 문서 확인과 기록 갱신. Docker 명령·Java 테스트는 실행하지 않았다.
- 남은 확인: Docker 엔진 연결, Compose 설정 검증, PostgreSQL 실행·접속, SQL CRUD, 컨테이너 재생성 후 데이터 유지.

다음은 Docker Desktop 실행 후 docker info, docker compose config --quiet, docker compose up -d, docker compose ps 순서로 확인한다. 설정 검증만 할 때는 비밀번호가 출력되지 않는 --quiet 옵션을 사용한다. 데이터 유지 검증에서 볼륨까지 삭제하는 docker compose down -v는 사용하지 않는다.

과제가 완료되면 명세서와 이 일지를 갱신하고 실제 변경에 맞는 커밋 메시지를 추천한다. 과제별 별도 섹션 대신 오늘의 학습 흐름으로 누적하며, 커밋·푸시는 별도 요청 없이 실행하지 않는다.

## 이후 DB 접속과 Spring 연결까지 이어간 흐름

다시 실행한 docker compose up -d 결과에서 postgres:18 이미지 다운로드, 네트워크와 taskapi_postgres_data 볼륨 생성, 컨테이너 시작을 확인했다. docker compose ps에는 127.0.0.1:5432 연결과 Up 상태가 표시됐다. 학습자가 공유한 결과이며 조력자가 직접 실행한 것은 아니다.

실제 접속은 docker compose exec postgres psql -U admin -d taskAPI로 진행했다. current_database(), current_user() 결과도 taskAPI와 admin이었다. 이후 예제와 연결 설정은 처음 제안한 이름 대신 실제 값을 사용한다.

practice_tasks 테이블을 만들고 \d 명령으로 구조를 확인했다. id는 BIGINT와 GENERATED ALWAYS AS IDENTITY, PRIMARY KEY를 사용하고, title은 VARCHAR(200) NOT NULL, description은 TEXT, status는 VARCHAR(20) NOT NULL로 작성했다. NOT NULL은 빈 문자열이나 공백을 막는 규칙과 다르다는 점을 안내했다.

두 업무를 INSERT하고 ORDER BY id ASC로 조회해 ID 1·2, 제목·설명과 TODO 상태를 확인했다. SQL 문자열은 작은따옴표로 감싸고, 문장 끝에 세미콜론을 붙인다. \d는 SQL이 아닌 psql 명령이다. ID를 INSERT 열에서 제외하면 DB가 자동 생성한다. ORDER BY를 명시하지 않은 조회 결과에는 순서를 기대하지 않는다.

UPDATE와 WHERE의 역할 및 조건 누락 시 전체 행이 변경될 수 있음을 안내한 뒤, 학습자가 연습 생략을 요청했다. SQL 수정·삭제는 실행 완료로 기록하지 않는다. 컨테이너 재생성 후 데이터 유지도 아직 확인하지 않은 채 Spring 연결 학습으로 넘어갔다.

build.gradle에는 Spring Data JPA starter와 PostgreSQL 드라이버를 추가하도록 안내했다. JPA starter는 객체와 관계형 DB를 연결할 기반을 제공하고, JDBC 드라이버는 Java와 PostgreSQL 사이의 통신을 담당한다. implementation과 runtimeOnly의 역할도 구분했다. application.properties에는 JDBC URL·사용자·외부 비밀번호 설정을 추가하고 ddl-auto=none으로 자동 테이블 변경을 하지 않도록 안내했다.

학습자가 IDE로 실행한다고 하여 실행 설정에서 비밀번호를 전달하는 방법을 안내했다. 공유 실행 로그에는 환경 변수 대신 -DPOSTGRES_PASSWORD 시스템 속성이 사용됐으며 Spring은 이 값으로도 설정의 placeholder를 채울 수 있다. Compose의 .env와 IDE에서 실행하는 Spring의 외부 설정은 자동으로 공유되는 것이 아니다. 비밀번호 값은 기록하지 않는다.

공유한 서버 로그에서 Hikari의 PostgreSQL 연결 생성, PostgreSQL 18.6과 taskAPI 접속 URL, JPA EntityManagerFactory 초기화, 8080 포트의 정상 서버 시작을 확인했다. JPA Repository가 0개인 것은 아직 작성하지 않은 단계에 맞는 결과다. open-in-view 경고는 연결 실패와 구분하고 트랜잭션 학습에서 함께 다루기로 했다.

전체 테스트 실행 여부에 대한 질문에는 매번 전체를 실행할 필요는 없으며, 이번에는 의존성과 DB 설정을 변경한 단계의 마무리로 기존 31개를 한 번 실행하도록 안내했다. 일반 단위 테스트와 Spring 컨텍스트 테스트의 DB 필요 여부를 구분하고 테스트 실행 설정에도 비밀번호를 전달하도록 안내했다.
