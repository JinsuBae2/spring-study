## 1. 시작 배경 — 10월 7일부터 이어진 내용

Java 21과 Spring Boot 프로젝트를 준비하고 업무 객체를 구현했다. Task는 제목·설명·상태를 갖고, 생성 시 TODO이며 제목이 null·빈 문자열·공백뿐이면 거부한다. 상태는 TODO → IN_PROGRESS → DONE 순서로만 바꿀 수 있다.

초기에는 고정 업무 조회와 생성 요청을 받아 반환하는 API를 만들었다. 처음에는 저장 기능이 없었지만, 오늘 메모리 저장과 조회를 연결했다.

초기 학습에서 확인한 내용:

- JSpecify의 @NonNull 자체는 런타임 검사를 추가하지 않으며 빈 제목 검증을 대신하지 않는다.
- `title == null || title.isBlank()`는 왼쪽이 참이면 오른쪽을 실행하지 않는다. 순서를 뒤집으면 null 입력에서 NullPointerException이 먼저 발생한다.
- 예외를 생성하는 new와 실제로 던지는 throw는 다르다.
- throws는 예외 발생 가능성을 선언한다. 현재 업무 규칙에 관계없는 IllegalAccessException 선언은 필요하지 않았다.
- IllegalArgumentException은 잘못된 인수, IllegalStateException은 현재 상태에서 허용하지 않는 작업에 사용했다.
- 예외를 던질 조건은 정상 상태가 아니라 허용하지 않는 상태여야 한다.

## 3. API와 역할 분리

| 요청 | 역할 | 응답 기준 |
|---|---|---|
| GET /tasks/sample | 고정 업무 확인용 | 200 |
| POST /tasks | 제목·설명으로 업무 생성·저장 | 200, 잘못된 제목 400 |
| GET /tasks | 저장 업무 전체 조회 | 200, 없으면 [] |
| GET /tasks/{id} | ID로 단건 조회 | 200, 없으면 404 |
| PATCH /tasks/{id}/start | 업무 시작 | 200, 없으면 404, 잘못된 상태 409 |
| PATCH /tasks/{id}/complete | 업무 완료 | 200, 없으면 404, 잘못된 상태 409 |
| PUT /tasks/{id} | 제목·설명 교체 | 200, 잘못된 제목 400, 유효 본문의 없는 ID 404 |

- TaskCreateRequest는 외부에서 받을 제목·설명을 담는 DTO다. ID와 초기 상태는 서버가 결정한다.
- DTO 분리의 핵심은 외부 입력과 업무 규칙을 분리하는 것이다. record는 데이터를 간결하게 표현하지만 일반 클래스로도 DTO를 만들 수 있다.
- record 필드는 재할당할 수 없지만, 내부에 담긴 가변 객체까지 자동으로 불변이 되는 것은 아니다.
- DAO는 데이터 전달 객체가 아니라 저장소 접근을 담당한다. 현재는 메모리 Repository를 사용하며 JPA·DB는 아직 도입하지 않았다.
- Repository는 저장·조회, Service는 업무 처리 흐름, Controller는 HTTP 요청·응답을 담당한다.
- 저장 결과 반환은 설계 선택이다. 현재처럼 전달받은 객체를 그대로 저장하면 void도 가능하고, ID 등이 반영된 저장 결과를 돌려주는 방식도 가능하다.
- 메모리 데이터는 재시작하면 사라진다. ArrayList 기반 저장소의 동시성 보장은 이번 범위에 포함하지 않는다.

## 4. 막힌 부분과 해결 과정

### ID와 목록 위치를 혼동했다

List.get()은 업무 ID가 아니라 0부터 시작하는 목록 위치를 받는다. ID 1인 업무가 목록 위치 0에 있어도 get(1)은 두 번째 업무를 가져온다. 범위를 벗어난 get()은 null이 아니라 예외를 발생시킨다.

처음에는 ID를 0부터 부여해 위치와 맞추려 했으나, 최종적으로 양의 정수 ID를 유지하고 각 업무의 ID를 비교해 찾도록 수정했다. 목록 크기로 번호를 부여하는 방식도 삭제 이후 중복 위험이 있어 별도 카운터로 바꿨다.

### 예외·응답 객체를 생성만 해서는 동작하지 않는다

예외는 throw로 던져야 하고, ResponseEntity는 Controller에서 반환해야 HTTP 응답이 된다. Repository에는 HTTP 처리 코드를 두지 않는다.

### 코드 수정 후 서버 재시작이 필요했다

목록에는 ID 1이 있었지만 단건 조회는 404가 나온 적이 있다. 재시작 후 새로 생성한 업무를 조회해 200을 확인했다. 코드와 실행 중인 서버가 같은 상태인지 확인해야 한다.

### Validation의 규칙과 실행 위치를 구분했다

DTO의 @NotBlank는 제목의 규칙을 선언하고 Controller 파라미터의 @Valid는 그 규칙을 실행하도록 연결한다. 잘못된 요청은 Controller 본문과 Task 생성자 실행 전에 거부된다.

Task 생성자 검증도 유지한다. HTTP 이외의 코드에서 직접 생성할 때도 업무 규칙을 지켜야 하기 때문이다.

### 중복 상태 검사와 없는 업무 검사는 다르다

TASK-009에서 Controller의 상태 비교를 제거하고 Task에 맡겼다. 이 과정에서 completeTask의 null 검사까지 제거해 없는 ID에서 500이 발생했다. null → 404 처리는 유지하고 상태 비교만 제거한 뒤 다시 검증했다.

### 테스트가 통과해도 의도와 다를 수 있다

중복 완료 테스트에서 completeTask 대신 startTask를 호출했다. 완료 후 시작도 예외를 던지므로 테스트는 통과했지만, 중복 완료를 검증하지 못했다. 이후 completeTask 호출로 수정했고 테스트 실행 통과를 확인했다.

## 5. 테스트에서 배운 것

- @Test: 실행할 테스트 메서드를 표시한다.
- @BeforeEach: 테스트마다 새 Repository와 Service를 준비해 데이터 영향을 분리한다.
- assertEquals(기대값, 실제값): 결과값이 기대와 일치하는지 확인한다.
- assertThrows(예외 타입, 실행할 코드): 해당 코드에서 지정한 예외가 발생하는지 확인한다.
- 예외 검증 뒤 저장소에서 다시 조회한 상태도 비교해 실패 요청이 상태를 바꾸지 않았는지 확인한다.
- 일반 자바 객체의 규칙과 Service는 생성자로 직접 연결해 테스트할 수 있다. SpringBootTest가 반드시 필요한 것은 아니다.
- HTTP 상태·JSON 응답 검증과 Service 단위 테스트는 확인하는 범위가 다르다.

## 6. 검증 결과와 남은 범위

| 항목 | 확인 결과 | 한계·남은 검증 |
|---|---|---|
| 메모리 저장·목록 | 학습자가 두 업무 생성 순서와 입력값 유지 결과 공유 | 재시작 직후 빈 목록은 명시적 실행 증거 미확인 |
| 단건 조회 | 조력자가 존재 ID 200·본문 일치, 없는 ID 404 확인 | TASK-010·011 변경 후 API 재검증 완료 |
| 상태 변경 | 정상 전환 200, 잘못된 전환 409, 실패 후 상태 유지, 없는 ID 404 직접 확인 | Service 분리 후 정상 전환·오류 본문·상태 유지·404 재검증 완료 |
| 제목 검증 | 빈 문자열·공백·null 모두 400과 INVALID_REQUEST 확인 | 오류 메시지 띄어쓰기 수정 후 응답 미확인 |
| 실패 요청 저장 | 공백·null은 요청 전후 목록 동일 | 빈 문자열은 오류 본문 비교에서 중단되어 저장 여부까지 미확인 |
| 정상 제목 | 생성 200·TODO·목록 저장 직접 확인 | 없음 |
| 전체 테스트 | ./gradlew test --console=plain: 25개 통과, 실패 0 | 중복 완료 테스트 수정 확인 |
| 테스트 구성 | 컨텍스트 1, Task 4, Repository 3, Service 17 | Task의 null·공백 제목 전용 테스트는 아직 없음 |

초기에 Task.complete() 전용 테스트 연습은 학습자 요청으로 생략했다. 이후 Service의 정상 완료·시작 전 완료 테스트가 추가됐고 실행 통과를 확인했다. 중복 완료 테스트의 대상 호출도 수정하고 실행 통과를 확인했다.

HTTP 오류 메시지는 계약과 정확히 맞춰야 한다. 앞서 ‘비어있을’과 ‘비어 있을’의 차이로 문자열 비교가 실패했다. 수정된 소스는 확인했으나 수정 후 응답 확인과는 구분한다.

터미널 응답 끝의 %는 줄바꿈이 없을 때 zsh가 표시할 수 있는 기호이며 API 오류가 아니다.

## 8. TASK-011 추가 학습과 완료 결과

- 처음에는 Controller 성공 응답 return과 @Valid @RequestBody가 빠져 있었다. 수정하여 요청 변환·검증·응답을 연결했다.
- Task.update는 제목을 검증한 뒤 두 필드를 변경하도록 했다. HTTP 입력 검증과 도메인 규칙 보호는 서로 다른 진입점을 담당한다.
- Service 테스트는 DTO 검증을 거치지 않으므로 도메인 검증이 필요하다.
- 설명이 null이면 기존 값을 보존하던 처리를 제거하고 요청값으로 교체하도록 맞췄다.
- 검증을 우회하는 제목·설명 setter를 제거하고 update로 변경 경로를 모았다.
- 처음 작성한 테스트 일부는 findById를 호출만 했다. 호출 자체는 검증이 아니며 반환값에 assertion을 적용해야 한다.
- 학습자 요청에 따라 조력자가 누락된 제목·설명·ID·상태·목록 순서 및 다른 업무 유지 검증을 보완했다. 일반 구현 코드는 학습자가 작성했다.
- Service 테스트 17개, 전체 25개 통과.
- HTTP 검증: 세 상태별 정상 수정, 단건·목록 반영, ID·상태·순서 유지, 다른 업무 보존, 세 종류 제목 오류 400·정확한 오류 본문·실패 후 데이터 유지, 빈 설명 수정, 없는 ID의 수정 404 통과.
- TASK-010 상태 API 회귀 검증도 통과했다.
- 검증용 업무 ID 1과 2가 메모리에 남아 있다. 최종 상태는 각각 DONE, TODO다.
- POST의 이전 미확인 항목은 별도이며 이번 PUT 검증으로 완료했다고 간주하지 않는다.

## 9. 기록과 학습 운영 방식

- 날짜별로 문서 하나에 누적하며 과제마다 별도 학습 파일을 만들지 않는다. 이 문서는 기존 파일 경로를 유지한다.
- 요구사항과 전체 진행 상태는 docs/task-api-requirements.md에서 관리한다.
- 과제 검증이 끝날 때 일지와 명세서를 갱신하고 실제 변경에 맞는 커밋 메시지를 추천한다. ‘오늘 공부 끝’이면 그날 내용을 전체적으로 재정리한다.
- 일반 구현은 학습자가 작성하며 도움 요청 시 코드나 힌트를 제공한다.
- 테스트에 한해 조력자가 준비 코드와 틀을 작성하고 학습자가 핵심 호출·검증을 채운다.
- 직접 실행 결과, 학습자가 공유한 결과, 미검증 항목을 구분한다. 학습자의 이해나 감정을 대신 작성하지 않는다.
- docs 저장을 기본으로 하며 외부 업로드·블로그 발행·예약 자동화는 설정하지 않았다.
