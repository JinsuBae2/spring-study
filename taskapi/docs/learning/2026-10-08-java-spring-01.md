# 2026-10-08 Java·Spring 학습 일지

- 프로젝트: 팀 업무 관리 API (`taskapi`)
- 목표: 직접 구현하고, 동작을 설명하며, 테스트와 HTTP 요청으로 검증하기
- 범위: 전날 시작한 업무 객체·첫 API를 바탕으로 메모리 기반 CRUD, 상태 변경, 검증·예외 처리와 Service 분리까지 진행
- 기준: 대화에서 확인한 날짜와 실행 결과를 사용한다. 정확한 구현 날짜가 확인되지 않는 초기 작업은 전날부터 이어진 배경으로 기록한다.
- 현재 상태: 메모리 기반 CRUD와 상태 변경 API의 구현·검증을 마치고 오늘 학습을 종료했다.

## 1. 시작 배경 — 10월 7일부터 이어진 내용

Java 21과 Spring Boot 프로젝트를 준비하고 업무 객체를 구현했다. Task는 제목·설명·상태를 갖고, 생성 시 TODO이며 제목이 null·빈 문자열·공백뿐이면 거부한다. 상태는 TODO → IN_PROGRESS → DONE 순서로만 바꿀 수 있다.

초기에는 고정 업무 조회와 생성 요청을 받아 반환하는 API를 만들었다. 처음에는 저장 기능이 없었지만, 오늘 메모리 저장과 조회를 연결했다.

초기 학습에서 확인한 내용:

- JSpecify의 @NonNull 자체는 런타임 검사를 추가하지 않으며 빈 제목 검증을 대신하지 않는다.
- `title == null || title.isBlank()`는 왼쪽이 참이면 오른쪽을 실행하지 않는다. 순서를 뒤집으면 null 입력에서 NullPointerException이 먼저 발생한다.
- 예외를 생성하는 new와 실제로 던지는 throw는 다르다.
- throws는 예외 발생 가능성을 선언한다. 현재 업무 규칙에 관계없는 IllegalAccessException 선언은 필요하지 않았다.
- IllegalArgumentException은 잘못된 인수, IllegalStateException은 현재 상태에서 허용하지 않는 작업에 사용했다.
- 예외를 던질 조건은 정상 상태가 아니라 허용하지 않는 상태여야 한다.

## 2. 오늘 구현한 흐름

처음에는 요청으로 받은 제목과 설명으로 업무를 생성하고 반환했다. 여기에 메모리 저장소를 연결해 생성한 업무를 목록으로 조회할 수 있게 했다. 서버가 양의 정수 ID를 부여하도록 하고, ID로 업무 하나를 찾거나 없는 업무에 404를 반환하는 기능을 추가했다.

다음으로 업무를 시작하고 완료하는 API를 만들었다. 정상 전환은 200, 잘못된 전환은 409로 응답하며 실패한 요청은 상태를 바꾸지 않도록 했다. 제목 검증은 DTO에 선언하고 공통 예외 처리기로 오류 코드와 메시지를 반환하도록 연결했다.

Controller에 있던 업무 처리 흐름은 Service로 옮겼다. 현재 구조는 Controller → Service → Repository이며, 제목과 상태의 업무 규칙은 Task가 담당한다. GlobalExceptionHandler는 검증 실패와 잘못된 상태 예외를 HTTP 오류 응답으로 변환한다.

제목·설명 수정도 추가했다. 두 값은 요청값으로 교체하고 빈 설명을 허용한다. 업무 상태와 관계없이 수정할 수 있지만 ID·상태·목록 순서와 다른 업무의 데이터는 유지한다. 잘못된 제목은 수정 전에 거부해 기존 제목과 설명을 보존한다.

마지막으로 업무 삭제를 구현했다. 모든 상태에서 삭제할 수 있고 성공하면 본문 없이 204를 반환한다. 삭제한 업무는 단건 조회와 목록에서 제외되며 다시 삭제하면 404다. 다른 업무와 상대적인 순서는 유지하고 삭제한 ID는 같은 서버 실행 중 재사용하지 않는다.

## 3. API와 역할 분리

| 요청 | 역할 | 응답 기준 |
|---|---|---|
| GET /tasks/sample | 고정 업무 확인용 | 200 |
| POST /tasks | 제목·설명으로 업무 생성·저장 | 200, 잘못된 제목 400 |
| GET /tasks | 저장 업무 전체 조회 | 200, 없으면 [] |
| GET /tasks/{id} | ID로 단건 조회 | 200, 없으면 404 |
| PATCH /tasks/{id}/start | 업무 시작 | 200, 없으면 404, 잘못된 상태 409 |
| PATCH /tasks/{id}/complete | 업무 완료 | 200, 없으면 404, 잘못된 상태 409 |
| PUT /tasks/{id} | 제목·설명 교체 | 200, 잘못된 제목 400, 유효 본문의 없는 ID 404 |
| DELETE /tasks/{id} | 업무 삭제 | 204와 빈 본문, 없으면 404 |

- TaskCreateRequest는 외부에서 받을 제목·설명을 담는 DTO다. ID와 초기 상태는 서버가 결정한다.
- DTO 분리의 핵심은 외부 입력과 업무 규칙을 분리하는 것이다. record는 데이터를 간결하게 표현하지만 일반 클래스로도 DTO를 만들 수 있다.
- record 필드는 재할당할 수 없지만, 내부에 담긴 가변 객체까지 자동으로 불변이 되는 것은 아니다.
- DAO는 데이터 전달 객체가 아니라 저장소 접근을 담당한다. 현재는 메모리 Repository를 사용하며 JPA·DB는 아직 도입하지 않았다.
- Repository는 저장·조회, Service는 업무 처리 흐름, Controller는 HTTP 요청·응답을 담당한다.
- 저장 결과 반환은 설계 선택이다. 현재처럼 전달받은 객체를 그대로 저장하면 void도 가능하고, ID 등이 반영된 저장 결과를 돌려주는 방식도 가능하다.
- 메모리 데이터는 재시작하면 사라진다. ArrayList 기반 저장소의 동시성 보장은 이번 범위에 포함하지 않는다.

## 4. 막힌 부분과 해결 과정

### ID와 목록 위치를 혼동했다

List.get()은 업무 ID가 아니라 0부터 시작하는 목록 위치를 받는다. ID 1인 업무가 목록 위치 0에 있어도 get(1)은 두 번째 업무를 가져온다. 범위를 벗어난 get()은 null이 아니라 예외를 발생시킨다.

처음에는 ID를 0부터 부여해 위치와 맞추려 했으나, 최종적으로 양의 정수 ID를 유지하고 각 업무의 ID를 비교해 찾도록 수정했다. 목록 크기로 번호를 부여하는 방식도 삭제 이후 중복 위험이 있어 별도 카운터로 바꿨다.

### 예외·응답 객체를 생성만 해서는 동작하지 않는다

예외는 throw로 던져야 하고, ResponseEntity는 Controller에서 반환해야 HTTP 응답이 된다. Repository에는 HTTP 처리 코드를 두지 않는다.

### 코드 수정 후 서버 재시작이 필요했다

목록에는 ID 1이 있었지만 단건 조회는 404가 나온 적이 있다. 재시작 후 새로 생성한 업무를 조회해 200을 확인했다. 코드와 실행 중인 서버가 같은 상태인지 확인해야 한다.

### Validation의 규칙과 실행 위치를 구분했다

DTO의 @NotBlank는 제목의 규칙을 선언하고 Controller 파라미터의 @Valid는 그 규칙을 실행하도록 연결한다. 잘못된 요청은 Controller 본문과 Task 생성자 실행 전에 거부된다.

Task 생성자 검증도 유지한다. HTTP 이외의 코드에서 직접 생성할 때도 업무 규칙을 지켜야 하기 때문이다.

### 중복 상태 검사와 없는 업무 검사는 다르다

TASK-009에서 Controller의 상태 비교를 제거하고 Task에 맡겼다. 이 과정에서 completeTask의 null 검사까지 제거해 없는 ID에서 500이 발생했다. null → 404 처리는 유지하고 상태 비교만 제거한 뒤 다시 검증했다.

### 테스트가 통과해도 의도와 다를 수 있다

중복 완료 테스트에서 completeTask 대신 startTask를 호출했다. 완료 후 시작도 예외를 던지므로 테스트는 통과했지만, 중복 완료를 검증하지 못했다. 이후 completeTask 호출로 수정했고 테스트 실행 통과를 확인했다.

### 수정 요청과 객체의 검증을 연결했다

수정 API를 처음 작성할 때 성공 응답의 return과 @Valid @RequestBody가 빠져 있었다. 요청 JSON 변환, 입력 검증, 성공 응답을 연결해 수정했다.

Task.update는 제목을 검증한 뒤 제목·설명을 변경하도록 했다. Service 테스트는 DTO 검증을 거치지 않으므로 객체 자체의 검증도 필요하다. 검증을 우회하는 제목·설명 setter는 제거하고 update로 변경 경로를 모았다.

설명이 null이면 기존 설명을 보존하던 처리도 제거했다. 이번 기능은 일부 값만 유지하는 방식이 아니라 제목과 설명을 요청값으로 교체하는 요구사항이기 때문이다.

### 삭제 후에도 ID와 목록 위치는 독립적이다

Repository는 ID로 조회한 Task 객체를 목록에서 제거한다. 가운데 업무를 삭제하면 뒤 업무의 목록 위치가 달라지지만 ID는 바뀌지 않는다. ID 카운터를 줄이지 않고 새 번호를 발급해 삭제한 ID를 재사용하지 않도록 했다.

## 5. 테스트에서 배운 것

- @Test: 실행할 테스트 메서드를 표시한다.
- @BeforeEach: 테스트마다 새 Repository와 Service를 준비해 데이터 영향을 분리한다.
- assertEquals(기대값, 실제값): 결과값이 기대와 일치하는지 확인한다.
- assertThrows(예외 타입, 실행할 코드): 해당 코드에서 지정한 예외가 발생하는지 확인한다.
- 예외 검증 뒤 저장소에서 다시 조회한 상태도 비교해 실패 요청이 상태를 바꾸지 않았는지 확인한다.
- 일반 자바 객체의 규칙과 Service는 생성자로 직접 연결해 테스트할 수 있다. SpringBootTest가 반드시 필요한 것은 아니다.
- HTTP 상태·JSON 응답 검증과 Service 단위 테스트는 확인하는 범위가 다르다.
- findById를 호출하기만 해서는 결과가 맞는지 확인되지 않는다. 반환값을 담아 제목·설명·ID·상태 등을 assertion으로 검증해야 한다.
- 수정 테스트는 단건·목록 반영, 빈 설명, 모든 상태의 수정, 잘못된 제목 거부와 실패 후 데이터 유지를 다뤘다. 누락된 검증은 학습자 요청으로 조력자가 보완했다.
- 삭제 테스트는 가운데 삭제 후 순서·데이터 유지, 마지막 업무 삭제 후 ID 미재사용, 저장되지 않은 객체 삭제의 영향, 세 상태별 삭제를 다뤘다. 기존 테스트와 유사해 학습자 요청으로 조력자가 6개를 작성했다.
- 일반 구현 코드는 학습자가 작성하고 테스트 틀 또는 요청한 테스트 보완은 조력자가 담당했다.

## 6. 하루 전체 검증 결과와 남은 범위

마지막 `./gradlew test --console=plain` 결과는 **31개 통과, 실패 0개**다. 구성은 컨텍스트 1개, Task 4개, Repository 6개, Service 20개다. 기존 테스트를 포함해 CRUD의 수정·삭제 추가 이후에도 실행 통과를 확인했다.

| 기능 | 확인한 결과 | 남은 범위 |
|---|---|---|
| 생성·목록 | 정상 제목 생성 200·TODO·저장, 두 업무의 생성 순서와 입력값 유지 | 모든 재시작 시나리오를 검증한 것은 아님 |
| 단건 조회 | 존재 ID 200과 업무 일치, 없는 ID 404 | Service 분리 후 재검증 완료 |
| 상태 변경 | 정상 시작·완료 200, 잘못된 전환 409와 오류 본문, 실패 후 상태 유지, 없는 ID 404 | 정상·실패 동작 확인 완료 |
| 생성 요청 검증 | 빈 문자열·공백·null 모두 400과 INVALID_REQUEST 확인. 공백·null은 저장되지 않음 | POST 오류 메시지 띄어쓰기 수정 후 응답과 빈 문자열 요청의 저장 영향은 미확인 |
| 수정 | 세 상태별 200·단건/목록 반영, 빈 설명 허용, ID·상태·순서·다른 업무 유지 | 확인 완료 |
| 수정 요청 검증 | 제목 세 종류 모두 400과 정확한 오류 본문, 기존 데이터 유지. 유효 본문의 없는 ID는 404 | PUT 결과를 POST의 미확인 항목과 혼동하지 않음 |
| 삭제 | 세 상태에서 204와 빈 본문, 삭제 후 조회·재삭제 404, 다른 업무·순서 유지, ID 미재사용 | 확인 완료 |
| 없는 업무 삭제 | 404이며 기존 목록 유지 | HTTP 처리에서 검증 |
| Task 단위 테스트 | 기존 4개 통과. 이후 Service 테스트에서 정상 완료·잘못된 전환도 확인 | Task의 null·공백 제목 전용 단위 테스트는 아직 없음 |

초기에는 Task.complete() 전용 테스트 연습을 생략했지만 이후 Service 테스트에서 완료 흐름을 검증했다. 중복 완료 테스트의 잘못된 대상 호출도 수정했다.

오류 메시지는 계약과 정확히 맞춰야 한다. ‘비어있을’과 ‘비어 있을’의 차이로 비교가 실패한 적이 있다. 수정 요청에서는 최신 메시지 일치까지 확인했으며 생성 요청의 미확인 범위와는 구분한다.

삭제 API 검증에서는 검증용 업무만 생성·삭제했다. 종료 시 목록은 최초 목록과 같고 기존 업무는 삭제하지 않았다. ID 카운터는 검증 과정에서 증가한 상태다. 앞선 수정 검증에서 남겼던 ID 1·2의 기록은 재시작 전 이력이며 현재 업무 상태를 뜻하지 않는다.

터미널 응답 끝의 %는 줄바꿈이 없을 때 zsh가 표시할 수 있는 기호이며 API 오류가 아니다.

## 7. 내 말로 정리 — 학습자가 작성한 내용 보존

> 오늘 이해한 것:
> - Controller는 HTTP 요청·응답을 처리하고, Service는 업무 처리 흐름을, Repository는 저장·조회를 담당한다.
> - 요청 DTO의 검증과 Task 내부 검증은 역할이 다르다. HTTP 외부에서 직접 호출해도 규칙을 지키려면 Task에도 검증이 필요하다.
> - 업무 ID와 목록 인덱스는 다르다. 업무를 삭제하면 위치가 달라지므로 ID를 비교해 찾아야 한다.
> - assertEquals는 기대한 결과값을 비교하고, assertThrows는 특정 예외가 발생하는지 확인한다.
> - 조회 메서드를 호출하는 것만으로는 테스트가 되지 않는다. 반환된 값이 맞는지 assertion으로 확인해야 한다.
> - 테스트가 통과해도 잘못된 메서드를 호출했다면 원하는 요구사항을 검증하지 못할 수 있다.
> 
> 아직 헷갈리는 것: Test 코드 작성 요령에 대해 더 공부 해야할거같다.

## 8. 오늘 마무리와 다음 학습

메모리 저장소 기반 CRUD와 상태 변경, 입력 검증, 공통 예외 처리, Service 분리까지 구현하고 검증했다. 오늘 학습은 여기서 마쳤다.

DB·JPA와 영속 저장은 아직 도입하지 않았다. 서버를 재시작하면 데이터가 사라지는 현재 범위를 유지하며 다음 요구사항은 학습을 재개할 때 정한다.

작업별 커밋 제목 후보는 다음과 같다. 실제 변경 범위에 맞춰 선택한다.

- Service 분리: `refactor: 업무 처리 흐름을 TaskService로 분리`
- 수정 기능: `feat: 업무 제목·설명 수정 API 추가`
- 삭제 기능: `feat: 업무 삭제 API 추가`
- 날짜별 기록 정리: `docs: 10월 8일 학습 기록 정리`

커밋 메시지를 추천했으며 조력자는 실제 커밋·푸시를 실행하지 않았다. 학습자의 커밋 여부는 확인하지 않았다.

## 9. 기록과 학습 운영 방식

- 날짜별로 문서 하나에 누적하며 과제마다 별도 학습 파일을 만들지 않는다. 이 문서는 기존 파일 경로를 유지한다.
- 요구사항과 전체 진행 상태는 docs/task-api-requirements.md에서 관리한다.
- 과제 검증이 끝날 때 일지와 명세서를 갱신하고 실제 변경에 맞는 커밋 메시지를 추천한다. ‘오늘 공부 끝’이면 그날 내용을 전체적으로 재정리한다.
- 일반 구현은 학습자가 작성하며 도움 요청 시 코드나 힌트를 제공한다.
- 테스트에 한해 조력자가 준비 코드와 틀을 작성하고 학습자가 핵심 호출·검증을 채운다.
- 직접 실행 결과, 학습자가 공유한 결과, 미검증 항목을 구분한다. 학습자의 이해나 감정을 대신 작성하지 않는다.
- docs 저장을 기본으로 하며 외부 업로드·블로그 발행·예약 자동화는 설정하지 않았다.
